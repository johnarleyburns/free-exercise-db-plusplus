# v1.11 cross-language WorkoutIntent audit

## Scope

This audit covers native WorkoutIntent models, decoding, validation, policy
selection, structured resolution statuses, weekday offsets, equipment
override ordering, stable explicit overrides, and offline package resources.
Python v1.10.1 remains unchanged as the semantic reference.

## Architecture and resources

The root `resources/intent-policies.json` records the shared policy identities;
Swift SPM and Kotlin/JVM bundle offline copies, and R installs an `inst`
resource. No runtime network or Python bridge is used. The JSON schema remains
0.1.0 and no artifact schema version was bumped.

## Language implementation

- Python: existing full resolver and generator retained unchanged.
- Swift: Foundation-only Codable/Sendable WorkoutIntent, typed result,
  explicit overrides, validation, partial-range TARGET helpers, and native
  resolver/profile construction.
- Kotlin: kotlinx.serialization data classes, validation, and native JVM
  resolver with Android-free core.
- R: validated list/S3 reader, resolver/profile construction, DB-aware exercise,
  equipment, and family validation, TARGET helpers, stable result-list output,
  and installed-package smoke coverage.

## Verification

Swift package tests pass, including all non-history fixtures, mismatch handling,
partial TARGET ranges, and the external temporary-directory consumer. R
fixture execution, package checks, and installed-package smoke tests pass with
the optional `testthat` dependency disabled. The host's Gradle 4.4 cannot
evaluate the checked-in Kotlin DSL; `scripts/test_kotlin_consumer.sh` is the
CI consumer gate on a current Gradle installation.

## Findings and limitations

The native bindings do not claim full history-aware TrainingState integration
or native plan generation. R's
`generate_plan_from_intent()` explicitly reports that generation is deferred;
it does not fake parity. These are v1.12 work, with Swift the priority.

## Fixture matrix

| Fixture set | Python | Swift | Kotlin/JVM | R |
| --- | --- | --- | --- | --- |
| non-history resolution fixtures (10) | PASS | PASS | PASS | PASS |
| history-aware resolution | PASS | deferred | deferred | warning-only |
| flagship generation | PASS | deferred | deferred | deferred |

The native fixture checks compare the stable result fields where the package
currently exposes them. They do not silently treat history or generation as
passing: those rows are deliberately marked deferred.

## Adversarial findings and fixes

- Python policy constants were moved to a packaged canonical policy resource;
  v1.10.1 fixture results remained unchanged.
- Swift and Kotlin previously replaced explicit TARGETs instead of merging
  nested range members; both now merge and validate all four canonical target
  sections.
- Swift/Kotlin/R previously treated any supplied profile as equipment
  authority; they now require non-empty explicit profile equipment, matching
  Python precedence.
- Swift result encoding previously omitted nullable contract fields; stable
  result serialization now retains null values.
- Native equipment output is sorted and, when a DB is supplied, restricted to
  the DB vocabulary.
- Duplicate/negative/range and unsupported vocabulary checks were added to the
  native validators.

## Release gate

Resolution model/API gate: implemented. Full v1.11 release gate: not yet
green because complete cross-language fixture execution and native generation
are not available in all package environments.
